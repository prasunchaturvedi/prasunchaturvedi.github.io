Ledgers and blockchain

A ledger records transactions shared among parties. A blockchain is one kind of distributed ledger technology (DLT): an append-only, replicated history in which each record is time-stamped, validated by the network and cryptographically linked to earlier records, so it cannot be altered retroactively without detection.

Worked example: three notebooks

Alice, Bob and Charlie each keep an identical copy of the expense notebook. If Bob erases “Bob pays Charlie 30” in his copy, the other two copies disagree with his and his version is rejected. Replication plus comparison replaces trust in a single record-keeper.

Bitcoin (Nakamoto, 2008) was the first large-scale use: digital cash transferred peer to peer without a central bank.

Why blockchain: counterparty risk and disintermediation

Counterparty risk is the risk that the other side defaults. Traditionally it is managed by trusted intermediaries (banks, clearing houses, escrow agents, notaries). Blockchain disintermediates: cryptography, shared validation rules and peer-to-peer consensus replace institutional trust, and anyone holding a copy can audit the ledger.

Example: a buyer in India and an unknown seller in Germany lock funds in an on-chain contract that releases payment once delivery is recorded, instead of paying an escrow bank.

Centralised database vs blockchain

AspectClient–server databaseBlockchain
ControlOne owner/administratorEvery stakeholder holds a replica
Integrity threatsInsiders and intruders can silently edit records; backups can be alteredEach block holds the previous block’s hash; edits break the chain
AvailabilitySingle point of failureSurvives node failures while honest replicas remain reachable
AssuranceHashed backups and paid third-party auditsIndependent verification by any node

Topologies: centralised (star — lose the hub, lose everything), decentralised (several hubs — lose one region), distributed (peer-to-peer mesh — any surviving node still holds the full ledger). Real example: Blockcerts anchors diploma hashes on a public chain so employers can verify a degree without contacting the university.

Core properties and timeline

  • Digital signatures: every entry is signed, giving authenticity and non-repudiation.
  • Immutability: confirmed data is computationally infeasible to change.
  • Cryptographic security: one-way hashes and public-key infrastructure.
  • Pseudonymity: users act through public-key addresses, not names.
  • Trusted computing base: a platform for smart contracts and dApps.

2008 Bitcoin white paper · 2009 genesis block · 2014–15 Ethereum and programmable contracts (“Blockchain 2.0”) · 2015 Linux Foundation’s Hyperledger · 2016 Bitfinex hack (about 120,000 BTC: exchange risk, not protocol failure) · 2018 EOS mainnet · 2020 Ethereum Beacon Chain · 2022 the Merge.

Five building blocks

  1. Cryptography — hashes, Merkle trees, key pairs.
  2. P2P network — node discovery and broadcast without gatekeepers.
  3. Validity rules — what a valid transaction is (signature, balance) and how state updates.
  4. Ledger — transactions grouped into linked blocks.
  5. Consensus — agreement on order and state when some nodes are faulty or dishonest.

The body carries the list of validated transactions.

Worked example: why tampering cascades

Block 1 stores “Alice → Bob 10”; Block 2 stores Hash(Block 1); Block 3 stores Hash(Block 2). Change Block 1 to “100” and its hash changes, so Block 2’s stored pointer no longer matches. Recomputing Block 2 breaks Block 3, and so on. The attacker must redo every later block faster than the honest network extends the chain.

Transaction workflow

  1. User signs a transaction.
  2. It is broadcast to peers.
  3. Nodes check it against the validity rules.
  4. Miners/validators bundle valid transactions into a candidate block.
  5. Consensus (for example Proof of Work) selects the block.
  6. The producer earns the reward; every node appends the block.
  7. The transaction gains confirmations and becomes practically irreversible.
